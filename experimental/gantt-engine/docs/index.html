Experimental Gantt engine documentation

The experimental Gantt engine is a framework-free DOM and SVG implementation for the PMIS migration slice. The React PMIS application remains the production implementation.

Use the documentation portal when you want a readable reference in a browser. Use your browser's built-in find command, such as Ctrl+F, to search the page. The portal is generated from the Markdown files in this directory, so the Markdown files remain the source of truth.

Vanilla Gantt engine architecture

Purpose and status

This document describes the implemented experimental engine in this directory. It extends the repository migration plan at ../../../.agent/doc/migration/005-gantt-vanilla-migration.md with the actual framework, Gantt, bridge, and test boundaries delivered by task 006.

The implementation is isolated from the React PMIS application. No React, Zustand, Next.js, Tailwind, Radix, or component-library code is imported. The experiment does not include the dashboard, right inspector, task dialogs, comments, labels, checklist, application routing, authentication, or persistence.

The control flow is event-oriented. A button click executes a named command. The command changes application state and invalidates named views. The scheduler coalesces invalidations, and each view refresh reads a new snapshot. No virtual DOM, component reactivity, hooks, or transparent dependency tracking exists.

Application lifecycle

createGanttEngine() validates all host elements, normalizes task input, calculates initial CPM criticality, constructs MiniApplication, registers views and commands, and returns an object with start(), dispose(), reloadSchedule(), setTasks(), getState(), and getSnapshot().

start() performs these operations in order:

  1. Build the first immutable-style render snapshot.
  2. Start the delegated action listeners.
  3. Start all registered views; each queues its initial refresh.
  4. Start timeline pointer and keyboard listeners.
  5. Attach task-list hover and two-way scroll synchronization listeners.

dispose() cancels gesture work, removes every listener attached by the engine, cancels delayed work, disposes views and commands, and rejects reuse. The engine does not own or remove its host elements.

Command delegation

Interactive HTML uses stable names such as:

<button data-action="schedule.reload">Reload schedule</button>
<input type="radio" data-action="timeline.set-scale" value="week">

ActionDelegator installs exactly one listener for each supported browser event:

  • click for buttons;
  • submit for forms;
  • change for inputs, selects, and textareas.

It walks from the event target to the root, finds the nearest supported element with data-action, and executes the same-named command through CommandBus. The payload contains source, the native event, eventType, action name, and root. The delegator does not contain business rules or rendering calls.

View refresh contract

Four views are registered: task-list, timeline, status, and project-brand. renderProjectBrand replaces the descendants of .project-top-nav__brand only; it renders the logo button (with the committed image or the fallback glyph) and the project-name button or its editing textbox.

invalidateAllViews(reason) marks each dirty. ViewHost records reasons and schedules one microtask. Repeated invalidations before that microtask are coalesced. refresh() is explicit and runs the registered render function. A failed refresh remains dirty but does not enter an automatic retry loop; the application error handler reports it.

The renderer owns descendants of taskListElement and timelineElement only. It may replace those descendants during refresh, but it does not mutate application state, execute commands, call the bridge, or apply scheduling rules.

Scheduler contract

Scheduler is the only abstraction around queued work:

  • microtasks coalesce view invalidation;
  • animation frames throttle pointer previews;
  • delayed work compacts an extended timeline after a 260ms idle period near the left edge for ordinary horizontal scrolling;
  • task-release compaction removes unused outer date ranges after an expanded schedule drag;
  • async jobs pass an AbortSignal to bridge operations.

Every returned job has cancellation and completion state. MiniApplication.stop() and dispose() call cancelAll(). This makes asynchronous ownership visible to auditors who expect queued calls, timers, or an explicit I/O scheduler.

Explicit row order

Row order is an explicit engine-owned concept, not a date-derived value. buildVisibleRows accepts a flat order of { type: "workstream" | "task", id } entries that fully determines the row sequence: workstream headers, task order, cross-workstream placement, and ungrouped rows. When order is omitted the function falls back to the historical date-sort, so callers and tests that predate the order model keep working unchanged.

defaultRowOrder seeds the initial order from the date-sort (headers first, then each workstream's date-sorted tasks, ungrouped last), so a fresh engine matches the previous deterministic layout. reconcileRowOrder keeps the order consistent as tasks and workstreams are created, renamed, or deleted: it drops entries for removed items, appends headers for new workstreams, and places new tasks after their owning header (or as a bare row when ungrouped).

The engine stores the order on state.rowOrder and reconciles it on every replaceTasks (task create/rename/delete, schedule load/replace) and on workstream create/delete. Because rows come from the order rather than a date sort, a horizontal drag that changes a task's date never re-ranks its row. reloadSchedule and setTasks reseed the order from the replacement data's date-sort. A reorder commit passes rowOrder through the existing commit/persist seam (alongside tasks and effects) so a future persistence backend can store it without rework; in the current in-memory demo the order is ephemeral.

reorder.js provides the vertical-reorder geometry: it maps a pointer row-Y over the visible rows to a new flat order and the resulting per-task workstream. A task's workstream is derived from its position in the order (the nearest preceding workstream header), so dragging a bar across a header both reorders it and reassigns its group. Dropping on an expanded header inserts into that workstream; dropping on a collapsed header or in a collapsed block is rejected (only expanded workstreams are drop targets); dropping below all groups makes the task ungrouped. reorderWorkstreamToIndex moves a whole workstream block (header and its tasks) to reorder groups relative to each other.

The engine keeps the timeline origin (state.minDate) stable during a drag preview. It is seeded to the earliest task minus a 7-day past buffer. When a schedule-affecting drag reaches the left low-water threshold, the controller prepends one viewport-sized date chunk and preserves the visible pointer/date coordinate. It does not re-anchor the origin once per snapped preview date.

On pointer release after range expansion, the engine trims only unused outer dates. The retained scope spans the earliest task start and latest task end, but never becomes narrower than the visible viewport. Left-edge releases align the scroll position to zero; right-edge releases align it to the maximum scroll position. Internal empty gaps and task-containing dates remain unchanged. replaceTasks (used by reloadSchedule and setTasks) reseeds the origin from replacement data.

The renderer owns the wireframe cell grid. settings.grid is normalized by src/grid.js and controls vertical/horizontal line visibility, major-line visibility, minor/major/row colors, and group/task fills. This keeps later user grid preferences at a stable settings seam instead of scattering display decisions across SVG paint code.

dependencies.js selects edges by precedence: all, selected chain, hovered direct, critical path, then none. Hidden/collapsed endpoints are excluded. It returns one continuous orthogonal route per edge. Normal routes enter the child from the left; cramped routes enter from above. Elbow, parent-exit, top-inset, and top-gap values are separate constants.

scheduling.js is pure. Dragging/resizing returns new tasks and before/after effects. Direct child movement clamps to the latest direct predecessor end. Moving a predecessor right pushes only violating descendants recursively and preserves their durations. Moving a predecessor left never pulls descendants backward. Unrelated tasks retain their dates and metadata.

forecast.js keeps PERT/CPM separate from drag propagation. It uses (optimistic + 4 * mostLikely + pessimistic) / 6, then computes earliest/latest dates, slack, project finish, and critical IDs.

Bridge separation

Application commands may import Gateway from bridge/index.mjs. Only the composition root may import concrete transports from bridge/transports.mjs. Renderer, interaction, model, scheduling, and forecast modules do not import transport or PHP details.

The demo injects InMemoryTransport. A future PHP integration replaces only that construction with FetchTransport; command names and view code remain unchanged. The complete wire format, security boundary, cancellation, versioning, and idempotency rules are in PHP_BRIDGE_CONTRACT.md.

Bill of manifest

Runtime dependencies

None. The experimental Gantt runtime uses only browser platform APIs and local ES modules. It does not import React, Preact, Vue, Svelte, morphdom, jQuery, Zustand, Tailwind, Radix, date-fns, or any other runtime package.

This is deliberate: the required features are narrow: named command dispatch, explicit view invalidation, scheduled work, strict transport envelopes, DOM task rows, and SVG timeline rendering. A general UI framework would add lifecycle and abstraction surface that this migration does not need.

Gantt engine JavaScript/PHP bridge contract

Status: experimental contract for task 006

Protocol version: 1.0

Runtime dependencies: browser/Node built-ins only

Purpose and boundary

The bridge gives application command handlers one stable way to call a named operation, regardless of whether the operation is handled in memory or later delivered to PHP over HTTP.

It has four responsibilities:

  1. create and validate a transport-neutral request envelope;
  2. serialize values into the shared JSON data model;
  3. coordinate timeout and caller cancellation;
  4. return every outcome as { ok, data, error, meta }.

The bridge is not a renderer, state store, domain service, generated RPC system, PHP client SDK, or automatic retry mechanism. This package contains no PHP server and chooses no PHP framework, database, or authentication system.

Non-negotiable import rule

Views, DOM renderers, SVG renderers, and interaction render loops MUST NOT import:

  • transports.mjs;
  • fetch-transport.mjs or in-memory-transport.mjs;
  • endpoint URLs, HTTP headers, PHP route names, or PHP function names.

The permitted dependency direction is:

button / delegated DOM event
  -> application command or controller
    -> Gateway.execute(operation, payload, options)

application composition root
  -> constructs InMemoryTransport or FetchTransport
  -> injects the transport into Gateway
  -> injects application commands into views/controllers

src/bridge/index.mjs exposes only the application-facing gateway, error vocabulary, and protocol version. src/bridge/transports.mjs is a separate, composition-root-only surface. The contract test scans view/renderer source for transport imports, direct network APIs, endpoint paths, and PHP details.

An application command may depend on Gateway. A view should depend on an application command such as commitScheduleChange(command), not on a transport. This preserves the intended event-oriented sequence: user event invokes command, command awaits I/O, application state changes, renderer receives new state.

Transport contract

A transport implements:

transport.send(requestEnvelope, { signal })
  -> Promise<responseEnvelope>

The transport MUST:

  • use the supplied composed signal for cancellable work;
  • return the shared response envelope rather than a transport-specific success;
  • throw BridgeError for delivery failures without a valid response;
  • never call a renderer, mutate application state, or apply Gantt domain rules.

The gateway owns the deadline. It combines the caller signal and timeout into the single signal passed to the transport. Fetch therefore has no second timer with different semantics.

Timeout and cancellation

The gateway creates one composed signal for every call:

  • caller abort produces CANCELLED;
  • gateway deadline produces TIMEOUT;
  • whichever occurs first wins;
  • listeners and timers are removed when the call settles;
  • the returned Promise resolves to a failure result.

The gateway races delivery against this signal, so it returns even if a custom handler ignores cancellation. Such work may continue. Transports and handlers must observe context.signal, stop expensive work, and avoid committing after abort where possible.

HTTP cancellation cannot prove PHP did not commit. A timed-out or cancelled mutation has an unknown remote outcome. Query current state or retry using the same idempotency key; never issue a new key for the same user intent.

atomically where required;

Versioning contract

Three versions remain distinct:

  1. protocolVersion controls common envelope and transport semantics.
  2. operationVersion controls one operation's payload/data schema.
  3. clientVersion identifies the deployed JavaScript build for diagnostics.

Protocol 1.0 uses major/minor notation, but this implementation negotiates an exact string: the response must echo the request version. A breaking envelope change requires a new major. Compatible diagnostic fields may be added inside meta without changing 1.0; a future minor must be explicitly supported by both client and server before it is emitted.

Operation evolution uses a new positive integer. PHP may support adjacent versions simultaneously and adapt each to one application service. Never infer operation schema from clientVersion.

Unsupported protocol or operation version returns a normalized PROTOCOL_ERROR or UNKNOWN_OPERATION, using a status that still permits the JSON error envelope to reach the client.
